## Phase 2: 头脑风暴 (调度 Brainstorming Skill)

**探索阶段**:
```
## 探索项目上下文

当前状态:
- 单体 Django 应用
- 5 个主要业务模块
- 复杂的模块间依赖
- 数据库 500GB，难以拆分

## 提出的拆分方案

### 方案 A: 按业务领域拆分
- user-service: 用户管理
- order-service: 订单系统
- payment-service: 支付系统
- inventory-service: 库存管理
- notification-service: 通知服务

**优点**: 边界清晰，团队自治
**缺点**: 初期数据一致性挑战大

### 方案 B: 前后端分离 + 逐步拆分
- 先拆分前端和后端
- 后端内部先模块化
- 逐步将模块独立部署

**优点**: 风险低，渐进式
**缺点**: 见效慢，技术债务仍在

### 方案 C: Strangler Fig 模式
- 逐步将功能从单体中抽取
- 保持现有系统运行
- 新功能直接做微服务

**优点**: 风险可控，平滑过渡
**缺点**: 过渡期维护两套系统

**推荐**: 方案 C (Strangler Fig) - 平衡风险和收益
```

## Phase 4: 迭代式分析

**Iteration 1 - 识别问题**:
```
分析发现：数据库耦合是最难解决的问题。

追问：当前数据库有哪些表？表之间的关系如何？
用户: 用户表、订单表、订单明细表、支付记录表、库存表...
订单表有用户ID、库存表有商品ID...
```

**Iteration 2 - 深入数据库拆分**:
```
基于表依赖关系，建议数据库拆分策略：

阶段 1: 垂直拆分
- 用户库: 用户表、用户配置表
- 订单库: 订单表、订单明细表
- 库存库: 库存表、库存流水表

阶段 2: 服务拆分
- 先拆分 inventory-service（风险相对独立）
- 再拆分 user-service（依赖较少）
- 最后拆分 order-service 和 payment-service
```

**Iteration 3 - 确认细节**:
```
关于数据同步：
- 选项 A: 双写 (应用层同时写新旧库)
- 选项 B: CDC (Change Data Capture)
- 选项 C: 事件驱动 (Event Sourcing)

用户选择: B (CDC) - 使用 Debezium
理由: 对应用代码侵入最小
```

## Phase 5: 关键决策

```
## 需要您确认的关键决策

1. 【拆分顺序】
   推荐: 先库存服务 → 用户服务 → 订单/支付
   理由: 库存相对独立，风险可控

2. 【数据同步方案】
   推荐: CDC (Debezium)
   理由: 应用无侵入，支持增量同步

3. 【通信方式】
   推荐: 同步 REST + 异步消息队列
   理由: 查询用 REST，事件用消息队列

4. 【部署平台】
   推荐: Kubernetes (托管)
   理由: 降低运维复杂度

5. 【监控方案】
   推荐: Prometheus + Grafana + Jaeger
   理由: 完整的可观测性
```

用户确认以上决策。
